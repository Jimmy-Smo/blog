你写 Python 写了十年，自认对计算机很懂。直到某天要改一段 C 扩展，编译器报了个段错误，你盯着指针看了半小时，不知道它指向哪，也不知道那块内存还在不在。你意识到自己一直在用一层很厚的壳，壳底下的事你从没真正处理过。

K&R 干的事，是把那层壳拿掉，让你看见下面没有魔法。

## 语言的设计哲学：信任程序员

C 有一个贯穿全书的前提：程序员知道自己在干什么，所以语言不该拦着他。

数组越界不检查，因为检查要花时间。指针可以随便转换，因为你知道自己在做什么。内存要手动分配释放，因为自动回收有代价。这些决定在今天看是危险的，在 1972 年是合理的：那时候的机器慢，编译器弱，操作系统的每一行都要算成本。

理解这个前提，你才能理解 C 的很多「怪」。它不是设计得不好，是它把选择权交给了你，而选择权总是双向的。

这也是它和现代语言最根本的分歧。Python 假设你会犯错，所以替你检查；C 假设你不会犯错，所以出事时它不管你。

## 数组、指针、字符串是同一个东西

这是全书最反直觉、也最重要的一段。

在 C 里，数组名在大多数表达式里会退化成指向首元素的指针。`a[i]` 等价于 `*(a+i)`，而 `*(a+i)` 又等价于 `*(i+a)`，所以 `a[i]` 和 `i[a]` 是同一个东西。这不是彩蛋，是定义。

字符串则是一个以零结尾的字节数组。`"hello"` 的类型是 `char[6]`，最后那个字节是 `\0`。所以你传给函数的不是字符串，是一个指针；函数不知道它有多长，只能一直读到零为止。

这三样东西在 C 里是同一个东西的不同写法，好处是你永远知道一条语句在机器上要做什么。没有隐藏的分配，没有偷偷的复制，没有看不见的间接层。坏处是任何一处越界都会变成别处的错误，而错误现场和肇事现场可能隔了几百行。

## 未定义行为是这本书的暗线

K&R 没怎么强调，但今天读它必须自己补上这个概念。

C 标准对很多操作不做规定：有符号整数溢出、越界访问、释放后使用、空指针解引用、序列点之间的多次修改。这些叫未定义行为，意思是编译器可以对它们做任何事，包括让你的程序看起来正常，然后在别处崩溃，或者干脆把你的整个分支优化掉。

理解未定义行为，比记住语法重要。它意味着 C 的「正确」不是「跑通了」，是「没有踩到任何未定义的地方」。这个思维方式可以直接迁移到别的领域：你测试通过，只说明你测的那条路径没踩到。

它还给了一个更一般的教训：规范里没写的地方，实现可以随便来。你依赖的任何「大家都这么做」的约定，都是脆弱的。

## 小语言的教育价值

两百七十多页讲完一门语言，每句话都在干活，没有一个例子是为了填充。

这种密度本身就是一种主张：一门语言的本质没有那么多东西可讲，剩下的都是库和生态。今天的技术书很少敢这么写，因为读者按页数衡量价值，出版社按页数定价。

它还有一个副作用：你读完会对自己写文档和写注释的方式产生一点羞耻感。你的文档里有几句是真正必要的，几句是在凑。

## 它的边界

它是 1988 年的书，覆盖 ANSI C89。C99 之后的变长数组、`stdint.h`、内联、restrict，它都没有。它也不教你工程：没有构建系统，没有测试，没有内存检查工具，没有「怎么写一个能被别人维护的 C 项目」。

而且它确实不安全。它的很多自由在今天是要用工具链和规范去补的，书里不会告诉你怎么补。ASan、UBSan、静态分析、编码规范，这些是读完之后另外要学的。

## 它真正的遗产

一种成本模型。

你写 Python 时，`a + b` 是一个动作。你写 C 时，你知道它是取两个地址、读两个值、做一次加法、写回一个地址，而每一次内存访问都可能命中缓存，也可能等几十个周期。这个差别决定了你看到性能问题时会怀疑什么。

这种直觉不需要你天天写 C，但需要你写过一次。之后你看任何语言的任何行为，都会多问一句：它在机器上到底是什么。

垃圾回收、闭包、切片、字符串不可变，这些在你手写过一次 `malloc` 之后，会从「语言特性」变成「设计选择」，而设计选择是可以被质疑的。
