评审一段代码，你看完，皱眉，说：「感觉不对，但我说不上来。」作者问哪里不对，你说可能是命名，可能是太长，可能是嵌套太深。会议就在这种模糊里结束了，代码照原样合了进去。

这本书的价值，是让你把「感觉」翻译成「哪一条」。

## 它只讲构造，这正是它的价值

McConnell 把开发分成问题定义、需求、设计、构造、系统测试、维护几个阶段，然后只讲构造，讲了九百六十页。

这看起来像个奇怪的选择：构造不是最没技术含量的阶段吗。但恰恰因为大多数工程书都在讲架构、讲流程、讲管理，很少有人把「怎么写一个子程序」讲到这个深度。而日常工作中，你 80% 的时间在构造。

它还有一个隐含主张：构造阶段的质量，比架构阶段更能决定代码的长期命运。架构错了可以重构，但如果命名混乱、边界不清、错误处理缺失，重构的代价会大到没人敢做。

## 它按决策组织，不按概念

变量怎么命名、数据类型怎么选、控制结构怎么写、子程序多长合适、参数怎么传、防御式编程做到什么程度、什么时候重构。每一章对应一类决策，最后给一份检查表。

这个结构的好处是它可以直接用。评审前翻到对应章节，逐条问：这个函数是不是超过一屏了，这个参数是不是超过七个了，这个错误处理是不是只写了 log 没做恢复。问题一旦具体，讨论就从「我觉得」变成「这条不满足」。

它的证据意识也少见。每提出一条建议，它会说这是来自某项研究、某个项目的数据，还是作者的经验。你觉得可疑的地方，可以去查它引的那份研究。这让它比「大佬说应该这样」的书可靠，也让你能判断哪些结论该打折扣。

## 几条真正有分量的

命名：名字应该说明「是什么」，不是「怎么做」。`getUserById` 好过 `fetchDataFromDb`，因为后者把实现细节写进了接口，而这个实现明天可能会变。

子程序长度：不是「必须小于 50 行」，是「一个子程序应该只做一件事，而一件事的边界由它的名字决定」。名字里出现「和」的时候，通常该拆。

参数：超过六七个就很难记住顺序。解决办法不是加注释，是把相关的参数收成一个对象，让名字承担记忆。

嵌套：超过三层就该抽函数。这不是审美，是人的工作记忆只有那么多。

防御式编程：对外的接口要校验，对内的调用可以信任。全都校验会让代码膨胀，全都不校验会让 bug 扩散。分界线画在系统边界上。

断言：用断言表达「这里绝不可能发生」。它和错误处理不是一回事：错误处理应对预期内的失败，断言抓的是程序员的错误。

## 重构的时机

书里给了一个反直觉的建议：不要等到代码烂了再重构，要在每次修改的时候顺手重构一点。这叫「童子军军规」的版本，但 McConnell 讲得更细。

他区分了「重构」和「重写」。重构是不改外部行为的内部调整，可以小步进行，每步都能测试。重写是换一套实现，风险大得多，而且经常掉进第二系统效应。

他的建议是：大部分时候重构，少数时候重写，而重写的触发条件应该是「架构已经无法支撑下一个需求」，不是「这段代码看着丑」。

## 它的边界

2004 年的书。并发模型、async/await、函数式写法、现代类型系统，它基本没覆盖。例子是 Java 和 C++ 的，有些今天看起来啰嗦。

它对测试的讨论不深。它讲构造，测试是另一个阶段，而现代工程实践里测试和构造是交织的。

它对「团队」的讨论也少。命名规范、代码风格这些事，最终是团队协商的结果，不是一个作者能规定的。

## 它真正给的

一种把直觉说清楚的能力。

你说「这段代码不好」，可能对，但没法教给别人，也没法在评审里形成共识。你能说出「这个函数有七个参数，其中三个是布尔开关，说明它承担了三个职责」，讨论才有落点。

工程能力的差距，很多时候不在知道多少，在能不能把知道的东西讲成别人可以执行的话。
